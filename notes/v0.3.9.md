# v0.3.9 · 更新链路收口

上一版加了应用内更新，但它是「发射后不管」：点完安装按钮，窗口关掉，剩下的事没人管。这一版把三处坑堵上，并顺手清掉堆积的安装包。

## 1. 更新有没有真的装成功，现在能看见

旧逻辑：启动安装器 → 立刻返回成功 → 1.2 秒后退出。安装器若因磁盘不足、杀软拦截、未签名策略、`[Run]` 项没触发而失败，用户只会看到托盘消失，或重启后还是旧版本 —— 和「正常更新」长得一模一样。

新增 `update-pending.json`（`%LOCALAPPDATA%\PeripheralBattery\`）：

- 启动安装器**之前**写入 `{from, to, installerPath, startedAt}`。
- 下次启动比对 `AssemblyVersion`：等于或高于 `to` → 判定成功，删标记，发一条「更新完成」通知；仍是 `from` → 判定失败，保留标记、丢掉那份安装包。
- 失败时：托盘通知一次（只发一次，标记里记 `notified`），设置页「软件更新」区块常驻一条红色提示，写明「上次更新到 vX 未完成，当前仍是 vY，请点检查更新重试」。

## 2. 升级后托盘不再消失（单实例锁竞态）

旧逻辑：新实例抢不到 `Local\PeripheralBattery_AppMutex` 就通知旧实例显示面板然后退出。而更新流程里旧进程是**自己**延迟 1.2 秒退出的，`[Run]` 拉起的新实例有概率抢先检查互斥锁 —— 抢不到就退出，最终结果是升级完成后桌面上一个托盘图标都没有。

新增 `Helpers/SingleInstanceLock`：拿不到锁时每 200 ms 重试一次，最多 5 秒；同时用 `WaitOne(0)` 判定，顺带修好「名字存在但没人持有」和「上一个持有者崩溃（AbandonedMutex）」两种误判。

## 3. 没有安装包的版本不再被当成可自动更新

旧逻辑：资产选择是 `Setup ?? 便携 EXE ?? zip`，只要拿到 `.exe` 就下载并启动。当某个 release 没有 Setup 资产时，会把便携单文件当安装器执行 —— 它忽略 `/VERYSILENT`，普通启动后又撞上第 2 条的互斥锁，用户在「安装中」的提示里等来一个消失的应用。

现在两道关卡：

- `SelectAssets` 只认文件名含 `Setup` 的 `.exe`，便携版和 zip 不再兜底；拿不到 → 打开 release 页面。
- `UpdateInstaller` 在下载前再校验一次文件名（`IsInstallerFileName`），不匹配直接返回 `noInstaller`。

顺带修掉一个潜在误判：GitHub 会把非 ASCII 资产名做百分号编码，旧代码拿编码后的名字去 `sha256.txt` 里找哈希，必然找不到，然后以「该版本没有发布校验值」取消更新。现在先解码再匹配。

## 4. 清理堆积的安装包

每版本一个 72 MiB 的安装器，之前只增不删。新增 `PruneStaleDownloads`：启动时删掉所有中断残留的 `*.part`，以及超过 2 天的 `*.exe`（正在运行的安装器会占用文件，删除失败就留到下次）。

## 验证

- 新增 10 项单测：标记判定（完成 / 失败 / 更高版本 / 空标记 / JSON 往返）、单实例锁（被占用时返回 null / 前一个实例退出后能抢到 / 新名字立即可得）、文件名解码、安装器名判定、清理规则。
- `dotnet test` 全绿；端到端升级链路在发布后用 `--update-selftest` 从 0.3.7/0.3.8 实测。
